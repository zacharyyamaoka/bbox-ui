§2 · How they come together

The slot model — seven “header layouts” are three slots and two enums

The board names seven header layouts (type compact, title badge, other tools/text, centered, folding left, folding right, play button + 15.1ms). Modelling those as a seven-way enum would be a mistake: the eighth one arrives next week. They are all the same RowContainer with three slots filled differently, plus two genuine enums.

The style model — one Appearance, not seven props on eleven components

Your board note asks for tldraw/Excalidraw’s Line (style, colour, thickness, opacity) and Fill (style, colour, opacity) “for all the shapes”. That is seven controls. Repeating them as props on every component is 77 props and seven chances to diverge. One object, accepted at every level and inherited downward, is seven FieldSpecs written once:

interface Appearance {
  line?: { style?: 'solid'|'dashed'|'dotted'|'none'; width?: 'thin'|'med'|'thick';
           color?: string; opacity?: number }
  fill?: { style?: 'none'|'semi'|'solid'|'pattern'; color?: string; opacity?: number }
}
// every bbox-ui component takes `appearance?: Appearance` and puts it on a CSS custom-property
// scope, so a child inherits unless it overrides.  `color` defaults to `currentColor`, which is
// how a token and a per-shape override are the same mechanism (§6e).

§4 · The schema decision

One schema per component has to drive five surfaces: TypeScript props, Storybook argTypes/Controls, the right-hand inspector inside the demos, Autodocs, and the registry item’s documentation. Criteria first.

Recommendation — E. Not because the others are bad, but because you already wrote it. packages/inspector/src/inspector/inspectorModel.ts (1398 lines) opens with: “Everything a stock tldraw primitive can be told, as one list of fields. That is a superset of Storybook’s argTypes on every axis except one.

The bug hiding in that table. InspectorControl conflates a declaration (label, kind, options, min/max) with a reading (value, unset, overridden, mixed). That is why it can only be produced by getPrimitiveInspectorModel(editor) — a function that needs a live tldraw editor. Split the two and the declaration half becomes portable, static, and exactly the shape argTypes wants. That split is the entire proposal’s load-bearing move.
// packages/schema/src/field.ts — zero dependencies, no React, no engine.
// A FieldSpec is the DECLARATION.  It never carries a value.
export type FieldKind =
  | 'segments' | 'swatches' | 'tiles' | 'number' | 'range'
  | 'toggle' | 'color' | 'text' | 'object'

export interface FieldOption { value: string; label: string; swatch?: string; path?: string }

export interface FieldSpec<T = unknown> {
  id: string                 // must be a real prop key — one test asserts it
  label: string
  kind: FieldKind
  group?: string             // 'Layout' | 'Appearance' | 'Behaviour'   (Shopify section)
  caption?: string           // Figma's second level, already in InspectorControl
  options?: FieldOption[]
  min?: number; max?: number; step?: number; unit?: string
  glyph?: string; paired?: boolean; fallback?: number
  hint?: string
  default: T
  structural?: true          // changes layout, so it is NOT an appearance control (§6b)
}

// A READING is a FieldSpec plus what the current subject(s) actually say.
// Storybook is the degenerate case: one subject, `mixed` can never happen.
export interface FieldReading extends FieldSpec {
  value: string | number | boolean | null   // null === mixed
  unset?: boolean; overridden?: boolean; disabled?: boolean
}

// packages/schema/src/storybook.ts — 1 pure function, unit-testable, no Storybook import.
const CONTROL: Record<FieldKind, string> = {
  segments: 'inline-radio', swatches: 'select', tiles: 'radio', number: 'number',
  range: 'range', toggle: 'boolean', color: 'color', text: 'text', object: 'object',
}

export function toArgTypes(fields: readonly FieldSpec[]) {
  return Object.fromEntries(fields.map((f) => [f.id, {
    name: f.label,
    description: f.hint,
    options: f.options?.map((o) => o.value),
    control: { type: CONTROL[f.kind], min: f.min, max: f.max, step: f.step },
    table: { category: f.group, defaultValue: { summary: String(f.default) } },
  }]))
}

export function defaultArgs(fields: readonly FieldSpec[]) {
  return Object.fromEntries(fields.map((f) => [f.id, f.default]))
}

// demos/playground/src/InspectorPane.tsx — the SAME array, the product panel.
import { Inspector } from '@bbox-ui/inspector'
import { readFields } from '@bbox-ui/schema'
import { portFields } from '@bbox-ui/core/port.fields'

export function InspectorPane({ selection, write }) {
  //           declaration      +  subjects  ->  readings (value | null for mixed)
  const readings = readFields(portFields, selection.map((s) => s.props))
  return <Inspector readings={readings} onWrite={(id, v) => write(selection, id, v)} />
}

Why not the other four

  • CVA — it is a className builder. VariantProps<typeof x> is genuinely useful for types, but a cva config carries no label, no caption, no unit, no min/max, no swatch colour, no ordering, and no mixed. In this repo cva appears only inside shadcn’s vendored components/ui/* (button, tabs, toggle, sidebar, field, input-group) — it is boilerplate that arrived with the CLI, not an authoring pattern. Leave it there; do not promote it.
  • zod → JSON Schema → RJSF — good runtime validation, but a swatch row, a tile grid of SVG paths, a drag-scrub with a fallback origin and a unit are not expressible in JSON Schema without a uiSchema sidecar — which is a second schema, i.e. the thing you are trying to avoid. And it adds a runtime dependency to a package whose whole pitch is that it has two.
  • hand-written JSON Schema — same sidecar problem, minus the type inference.
  • argTypes only — lives in story files, so the product inspector cannot import it without importing Storybook into the product.

Keep TypeScript as the source of types, and the fields array as the source of controls. react-docgen already feeds Autodocs from the props interface; the as const satisfies readonly FieldSpec[] plus one test asserting every field.id is a real prop key is what stops the two drifting.

§5 · One storybook, three hosts

You asked to see every component live inside a React Flow and a tldraw whiteboard, with the same controls. Storybook has exactly the seam for it: a global declared in globalTypes gives you a toolbar dropdown, and a global decorator reads context.globals and decides what tree the story mounts inside. One global, one decorator, every story — including ones written next year — becomes viewable in all three hosts for free.

// .storybook/preview.tsx — one global, one decorator, three hosts.
import type { Preview } from '@storybook/react-vite'
import { DomHost, ReactFlowHost, TldrawHost } from '../demos/story-hosts'

const HOSTS = { dom: DomHost, reactflow: ReactFlowHost, tldraw: TldrawHost }

const preview: Preview = {
  globalTypes: {
    host: {
      description: 'Render this story in a plain div, a React Flow node, or a tldraw shape',
      toolbar: {
        title: 'Host',
        icon: 'component',
        items: [
          { value: 'dom',       title: 'DOM' },
          { value: 'reactflow', title: 'React Flow' },
          { value: 'tldraw',    title: 'tldraw' },
        ],
        dynamicTitle: true,
      },
    },
  },
  initialGlobals: { host: 'dom' },
  decorators: [
    (Story, context) => {
      const Host = HOSTS[context.globals.host as keyof typeof HOSTS] ?? HOSTS.dom
      return <Host><Story /></Host>     // the story is the node's / shape's body
    },
  ],
}
export default preview
// demos/story-hosts/TldrawHost.tsx — lives in demos/, so core keeps zero engine imports.
// The ShapeUtil is defined ONCE at module scope; a per-story class re-registers
// the shape on every render and tldraw throws.
class StoryShapeUtil extends ShapeUtil<StoryShape> {
  static override type = 'story' as const
  getDefaultProps() { return { w: 320, h: 200 } }
  getGeometry(s) { return new Rectangle2d({ width: s.props.w, height: s.props.h, isFilled: true }) }
  component() { return <HTMLContainer>{useStoryBody()}</HTMLContainer> }   // ← the story
  indicator(s) { return <rect width={s.props.w} height={s.props.h} /> }
}
  • The three host wrappers live in demos/story-hosts/. Never in the core — the moment packages/bbox-ui imports tldraw, the one rule that makes a third host a 150-line afternoon is gone.
  • The tldraw host needs a fixed-height container and the shape registered once at module scope. A ShapeUtil class created per render re-registers the shape and tldraw throws.
  • A story that reads context.globals.host itself is a smell — the story should not know. Only the decorator knows.

“A storybook-like inspector panel on the right” — which one is it?

Both, and that is fine, because they render the same array.

  • Inside Storybook it is the stock Controls addon, fed toArgTypes(fields). Do not replace it — you would lose Autodocs, the args URL state and the reset-to-default plumbing for free.
  • Inside the demos and, later, the product it is a copy-in <Inspector> — the one in packages/inspector, 71 files, which already has the drag-scrub field, the colour well, the segmented tiles and the swatch rows — fed readFields(fields, selection).
  • The product panel is the harder of the two: it must handle N subjects and render mixed. Storybook’s Controls is its degenerate single-subject case. Build the product one; Storybook’s comes free.

§6 · What you are not seeing

a · The schema is the product; the panel is a consequence

The Shopify insight you pointed at is not the panel — it is that a section’s settings and its presets are data in the same file, and the editor is generated from them. Your nine presets (Type, Function, Type Mapping, Class, Component, System, For, While, Conditional) are precisely Shopify presets: named bundles of setting values. And a Storybook story is also a named bundle of arg values. They are the same object. One presets.ts can be all three: the stories’ args, the inspector’s preset picker, and the toolbar’s “new Block of kind X” defaults. Write it early, not last.

Novelty check: the vault has zero references to Shopify’s theme editor or settings_schema.json, and Storybook appears twice in passing (a 2026-07-16 deep-research citation about docs tabs, and a note that Penpot’s design system uses it) with no analysis and no decision. This is new ground, not a restatement.

b · hidden is structural — so it cannot be an appearance control

Your board is emphatic: “Completely remove it, we don’t want it to be selectable either. If you just set 0 opacity, it could not be there but still capture mouse clicks.” Right — and the consequence goes further than hit-testing. Removing a port row reflows the block, which changes what blockLayout.ts returns, which changes what detach draws and what the compare harness measures. A visible toggle filed under Appearance would be a bug that only surfaces at detach time, in the other host. Mark it structural: true in the FieldSpec and keep it out of the Appearance group. SystemSketch already models it correctly — visible: boolean on BlockPort, with hiddenPortSummaries() doing the reflow and the “+N more” line.

c · “Detect polarity dynamically” contradicts the rule the repo rests on

If polarity is derived from what is connected, the core has to know about edges. It must not — ARCHITECTURE.md: “interaction geometry is host-owned and never travels”, and the core has “zero imports of tldraw, zero imports of React Flow”. Resolution: polarity is authored, with a default derived from which array the port sits in (inputs → W, outputs → E). A host that can compute a better one from its own edge graph passes it down as a prop. The direction of the flow is decided at the landing, by the host — which is already your ruling for cables.

d · “Everything is a Block” collides with Storybook’s per-component story tree

If members are Blocks, a Block story’s members arg is an array of Block args, and Storybook’s object control renders that as a raw JSON editor — technically correct, practically unusable. The stock answer is argTypes.mapping: the control offers short option strings and the mapping holds the real complex values.

argTypes: {
  members: {
    control: 'select',
    options: ['none', 'three', 'nested'],       // what you click
    mapping: {                                  // what the component receives
      none:   [],
      three:  [PRESETS.component, PRESETS.component, PRESETS.component],
      nested: [{ ...PRESETS.system, members: [PRESETS.component] }],
    },
  },
}

And the recursion does not need a “member story tree”: a member is a Block, so Block.stories.tsx covers it. What you do want is one story per containment rule — stack vs free, fill vs own width, black-box on vs off — because those are the rules that break.

e · Unstyled now, styled later — which rows are tokens and which are props

The rule that survives: if two blocks on one board may legitimately differ, it is a prop; if they must agree for the board to look like one product, it is a token.

token (theme.css, --bbox-*)prop (FieldSpec)
the rung scale itself — { md: 24, lg: 36, xl: 44, }which rung: size: 'sm'|'md'|'lg'|'xl'
port diameters { sm: 14, md: 25, lg: 36, } and ICON_RATIO 0.9size, and diameter for an exact override
hairline colour, radius, default gap/gutter, the sans/sketch/mono familiesfont, align, justify, padding
line thickness scale (thin/med/thick → px)line.width — which rung

The trap is line colour. The board lists it under Line, i.e. a prop — but nine times in ten you want the token. Make line.color default to currentColor: it inherits the theme unless someone overrides it, so the token and the per-shape override are one mechanism rather than two that fight.

f · The real cost per component is not the component

ARCHITECTURE.md’s second detach rule: “Geometry from the layout authority — the detached picture derives from layout.ts + blockLayout.ts, never from re-measured DOM, never hand-typed offsets.” So every new component needs a pure box function, or it cannot detach, cannot rebuild, and cannot be compared across the two hosts at 0.00px. The honest per-component cost is six artefacts:

component.tsx + component.fields.ts + layoutComponent() + DetachableKind + registry item + Component.stories.tsx

Eleven components × six is the budget. That is why §7 starts with one component all the way through rather than eleven components half way.

h · Registry granularity

Today’s 5 items already have exactly this shape, with bbox-layout as the shared lib dependency. Keep it; add glyph, text-box, pill, row-container, port-edge as siblings rather than folding them into block.

i · Storybook’s weight, honestly

  • Ladle is a genuine alternative: CSF-compatible, ~250KB of assets against Storybook 6.4’s 5.1MB by its own README. Its documented controls are boolean, number, range, select, multi-select, radio, inline-radio, check, inline-check — with no documented colour control, no object/array control, no mapping, no custom global toolbar, and no play functions. Those absences are precisely the three features this plan needs.
  • Tailwind v4 + Storybook 9 + Vite has real friction, all documented in the open: @tailwindcss/vite is not picked up by Storybook’s own Vite instance; ERR_PACKAGE_PATH_NOT_EXPORTED on @tailwindcss/vite/package.json; a crash when mergeConfig is imported at the top of main.ts on SB 9.1.1 / Vite 7.1.1. The fix is known and small: add the plugin inside viteFinal, with a dynamic import. Budget an hour, not a day.
  • The tldraw host inside Storybook is the one genuinely unproven piece of this plan. It should be the first thing T0 builds, not the last — if it does not work, the three-host toolbar becomes a two-host toolbar and the rest of the plan is unchanged.
